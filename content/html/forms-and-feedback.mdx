## The problem

A contact form that looks complete can still be difficult to use. Placeholder text disappears when someone starts typing, and a submit button may suggest that a message was sent when no service receives it.

## Concept

Each input needs a visible label. Connect `label for` to the input's `id` so clicking the label moves focus to the control. Choose an input type that matches the expected value, and use `required` only when the value is genuinely required. Group related fields in a `fieldset` with a `legend` when the group needs a name.

## Example

```html
<form action="/contact" method="post">
  <div>
    <label for="name">Your name</label>
    <input id="name" name="name" autocomplete="name" required />
  </div>
  <div>
    <label for="email">Email address</label>
    <input id="email" name="email" type="email" autocomplete="email" required />
  </div>
  <div>
    <label for="message">Message</label>
    <textarea id="message" name="message" rows="5" required></textarea>
  </div>
  <button type="submit">Send message</button>
</form>
```

## How it works

The `name` attributes identify values when a form is submitted. `type="email"` gives the browser a basic email format check and an appropriate mobile keyboard. `autocomplete` helps the browser offer stored values. Browser validation is useful feedback, but a real server must still validate submitted data.

The example's `/contact` action is only a placeholder. Do not publish a form with a “Send message” button until that endpoint works. In a static portfolio, show an email link instead, or clearly label the form as a demo.

## Common mistakes

- Treating a placeholder as a label.
- Giving several controls the same `id`.
- Using a `div` styled as a button rather than a real `button`.
- Saying “Message sent” after a front-end animation when nothing was transmitted.

## Practice

Create a name, email, and message form. Use Tab and Shift+Tab to visit every control. Click each label and verify it focuses the correct input. Submit with an empty required field and observe the browser's response. Then try an invalid email.

## Build

In the [HTML workshop](/learn/html/workshop?focus=forms), add a labeled form as a demo. The preview stays in your browser and does not send messages. If you later add a backend, test success and failure states with real requests.

## Checkpoint

You can explain the difference between `id` and `name`, and every form control has an associated label. Your page accurately states whether the form works.
