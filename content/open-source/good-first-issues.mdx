## The problem

A new contributor wants real work but cannot tell which issues are small enough to attempt independently.

## Concept

A good first issue has a bounded goal, a location in the code or content, acceptance criteria, and a way to verify success. Labels can help, but read the issue itself; a label is not a guarantee that the task is still available or easy.

## Example

```text
Example only: Clarify the explanation of response.ok
Area: content/javascript/
Change: add one checked response example
Done when: the practice task covers a 404 response
Verification: preview the lesson and run the content checks
```

This is a static example, not a live ZERO → HERO issue. See [actual open issues](https://github.com/CharlieJamesGwapo/zero-to-hero/issues) or [issues labeled good first issue](https://github.com/CharlieJamesGwapo/zero-to-hero/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22).

## How it works

Good beginner tasks may involve documentation, content, frontend behavior, accessibility, testing, bugs, or design. Read the discussion, confirm the issue is open, and ask a focused question if the acceptance criteria are unclear. A maintainer may assign the task or suggest a smaller scope.

## Common mistakes

- Assuming a label means nobody else is working on the issue.
- Choosing a large feature as a first change because it sounds impressive.
- Claiming a static example is a real open issue.

## Practice

Find an open issue in a repository you use. Write down its expected file, one measurable result, and the command or manual check that would prove it. If you cannot answer those, ask for clarification before coding.
