## The problem

“Improve the lesson” is too vague to review. A contributor needs a clear problem, a bounded result, and a way to know when the change is done.

## Concept

GitHub Issues are records for bugs, features, documentation, accessibility, performance, refactoring, and content improvements. A good issue explains the current behavior, desired outcome, and acceptance criteria without dictating every line of implementation.

## Example

```text
Title: Explain HTTP errors in the Fetch lesson
Type: Documentation · Difficulty: Beginner

Problem: The current example does not explain why fetch resolves
when the server returns an HTTP error status.

Goal: Explain response.ok and useful status handling.

Acceptance criteria:
- Explain response.ok and status codes.
- Show one checked response example.
- Add a common mistake and a practice task.
```

This is an **example issue**, not a claim that it exists in the repository.

## How it works

Maintainers triage issues, ask questions, label them, and may close or revise them when the product direction changes. A pull request can reference an issue so the proposal and its reason remain connected.

## Common mistakes

- Opening a duplicate issue without searching first.
- Posting passwords, tokens, or private user data in a public issue.
- Starting a large change without checking whether maintainers want it.

## Practice

Visit the [actual ZERO → HERO Issues page](https://github.com/CharlieJamesGwapo/zero-to-hero/issues). Search before opening an issue. Draft a small content issue with a page URL, one concrete problem, and two acceptance checks.

## Checkpoint

Could another contributor pick up your issue without a private explanation? If not, what information is missing?
