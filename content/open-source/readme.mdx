## The problem

A stranger finds your code but cannot tell what it does, how to run it, or whether it is maintained. Good code cannot solve missing setup instructions.

## Concept

A README is the project's front door. It should answer purpose, main behavior, prerequisites, installation, development, tests, deployment, contribution, and license. Include screenshots when they help someone evaluate a visual product; keep them current.

## Example

```text
# Project
What problem it solves
Features and tech stack
Screenshots or demo link
Requirements and installation
Environment variables (names, never secret values)
Run, test, and build commands
Deployment notes
Contributing and license
```

Read the [ZERO → HERO README](https://github.com/CharlieJamesGwapo/zero-to-hero#readme) as a real example, then compare the commands with `package.json`.

## How it works

A new contributor should be able to clone, install, run, locate the relevant source, preview an edit, and check it without private guidance. Keep the shortest successful path near the top; move deep architecture detail into linked docs.

## Common mistakes

- Leaving template instructions after the project changes.
- Listing environment variables without explaining whether they are required.
- Copying a screenshot that no longer matches the current UI.

## Practice

Ask someone who has not seen your project to use only its README to run it. Record every place they had to guess. Revise the document, then repeat the attempt.

## Checkpoint

Can a new contributor reach a working page and run checks using only the README? Name one fact the README should link out to rather than duplicate.
